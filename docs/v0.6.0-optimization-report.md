# v0.6.0 数据驱动优化报告

> 基于 REQ001（PSDT-Agent 框架，full 模式，cli-tool）首次实战数据。

---

## 一、实战暴露的问题与改善措施

### 🔴 P0-1: Handoff 完成回报机制失效

**现象：** 所有 5 个 handoff 的完成回报区域全部为空（status/output_files/read_files/summary 均未填写）。

**影响：**
- PM 的 Step 0 白名单校验完全失效（无 read_files 可对比）
- 质量门禁缺少 SubAgent 自述信息（无 summary）
- Handoff 协议——框架角色隔离的核心机制——形同虚设

**根因分析：**
SubAgent 在独立子会话中运行，它写入了产出文件（output/、code-report.md），但没有回到 handoff 文件中填写完成回报。这是 Claude Code SubAgent 机制的行为特征：SubAgent 倾向于"完成任务就结束"，而非"回到协议文件中做记录"。

**改善措施（三层防御）：**

| 层级 | 措施 | 文件 |
|------|------|------|
| 预防 | handoff 模板完成回报区增加醒目强制提示：`<!-- ⚠️ SubAgent 必须在结束前填写本节 -->` | templates/handoff-template.md |
| 容错 | PM 调度循环 Step 6 增加"回报缺失时 PM 代填"逻辑——根据产出物实际情况推断并标注 `[PM 代填]` | agents/pm.md |
| 检测 | verify.sh C 类增加 phase=done 时所有 handoff 回报非空检查 | scripts/verify.sh |

**设计思路：** 不能只靠"告诉 SubAgent 要填"（第一层已经失败了），必须有容错（PM 代填）和检测（verify.sh 报警）。三层中任何一层生效都能缓解问题。

### 🔴 P0-2: process.log 仅 2 行

**现象：** 整个 43 分钟的执行过程（14 Task、4 Batch、4 SR Gate），process.log 只记录了 INIT-1 的 2 行心跳。

**影响：**
- 无法做耗时分析（哪个阶段卡了？哪个 Task 最慢？）
- 无法做回溯审计（出了问题查日志）
- 断点恢复时缺少过程记录
- 框架自己定义的"PM 每步打印心跳"规则被违反

**根因分析：**
logging-standard.md 定义了"追加日志到 process.log"的规范，但只是描述性的。PM 在实际执行中将心跳打印到 stdout（对话中可见），但没有执行 `echo >> process.log` 的写入动作。规则是"应该做"而非"必须做+怎么做"。

**改善措施：**

| 层级 | 措施 | 文件 |
|------|------|------|
| 规范强化 | logging-standard.md 增加"强制落盘规则"——明确写入命令格式、写入时机、最低行数要求 | templates/logging-standard.md |
| 检测 | verify.sh C 类增加 process.log 存在性 + 行数下限检查（fast≥6, standard/full≥10） | scripts/verify.sh |

**设计思路：** 将"应该做"升级为"必须做+具体怎么做+做不到会被检测到"。给出具体的 echo 命令模板，降低 PM 的执行门槛。

### 🟡 P1-1: SR3 覆盖率标准与实际执行不一致

**现象：** SR3 通过标准写死"需求覆盖无遗漏（覆盖率 = 100%）"，但实际 REQ001 以 93% 覆盖率通过了 SR3（48/50 FR + 5/7 NFR）。

**影响：**
- 标准与执行不一致，削弱框架可信度
- 过于刚性的标准在实际中必然被绕过，不如设计合理的弹性机制

**根因分析：**
100% 覆盖率在理论上正确，但实际中总有非阻塞的轻微缺失（如某个 skill 文件少 1 个、某个非核心 NFR 未实现）。关键不是数字是否为 100%，而是未覆盖项是否有降级机制。

**改善措施：**

| 措施 | 文件 |
|------|------|
| SR3 标准改为"覆盖率 ≥ 95%，且未覆盖项均有降级机制或补充计划" | skills/mh-apply.md |
| SR3 决策上下文卡增加"降级项确认"区域（未覆盖需求 + 对应降级机制） | skills/mh-apply.md |

**设计思路：** 从"刚性数字"转向"数字+质性判断"。95% 是底线，剩余 5% 必须有明确的降级方案——这比假装 100% 更诚实也更实用。

### 🟡 P1-2: .venv 被归档到 output/

**现象：** deliverables/REQ001/output/ 下包含完整的 .venv/ 目录（Python 虚拟环境，数百个文件），导致产出物体积膨胀。

**影响：**
- 归档体积从实际 ~8000 行代码膨胀到 47MB
- 不是交付物，不应出现在产出中
- 后续 verify.sh 检查文件数量时会产生误导

**根因分析：**
mh-archive.md ARC-3 只说"直接复制全部文件"，没有排除规则。DE 在开发时在 output/ 下创建了 .venv（正常的 Python 开发行为），归档时被原样复制。

**改善措施：**

| 措施 | 文件 |
|------|------|
| ARC-3 增加归档排除规则（.venv/, node_modules/, __pycache__/ 等） | skills/mh-archive.md |
| verify.sh B 类增加 phase=done 时 output/ 不应包含开发环境目录的检查 | scripts/verify.sh |

### 🟡 P1-3: spec/ 归档不完整

**现象：** spec/ 下只有 _templates/（产出物自带的模板），没有 requirement-spec.md 和 design.md。

**影响：** ARC-1/ARC-2 的归档步骤可能没有正确执行，spec/ 作为"规格归档"目录名不副实。

**改善措施：**

| 措施 | 文件 |
|------|------|
| verify.sh B 类在 phase=done 时增加 spec/design.md（standard/full）和 spec/requirement-spec.md（full）的存在性检查 | scripts/verify.sh |

### 🟢 P2-1: Agent 超时无处理规则

**现象：** 3/14 任务超时（T-03, T-05, T-09），其中 T-05 需重试，T-03/T-09 代码已完整无需重试。框架没有定义"超时但代码完整"的处理规则。

**改善措施：**

| 措施 | 文件 |
|------|------|

**现象：** T-12/T-13/T-14 合并为一个 code-report-t12-13-14.md，违反逐 Task 独立约定。

## 二、Metrics 数据驱动改善的设计思路

### 2.1 为什么需要 metrics

框架的前五轮优化（v0.5.0-v0.5.4）全部是**静态分析**——读代码、找冗余、猜问题。这种方式有两个根本局限：

1. **无法发现"设计正确但执行失败"的问题**：handoff 模板设计得很好，但 SubAgent 就是不填——这在静态审视中看不出来
2. **边际收益递减**：到 v0.5.3 时，改动量已从 565 行降到 50 行级别，说明静态可发现的问题已接近枯竭

metrics.md 的引入将优化模式从"读代码猜问题"转向"跑需求看数据"。

### 2.2 metrics 的数据模型

```
执行指标 = {
  基本信息: { 耗时, 模式, 产出类型 }
  角色效能: { 派发次数, 驳回次数, 驳回原因 }
  修复循环: { 轮次, 收敛性, 根因分类 }
  SR 审批:  { 各节点通过/驳回次数 }
  异常事件: { 断点恢复, 超时, 其他 }
  质量指标: { 测试通过率, 需求覆盖率, 代码规范 }
  流程效率: { 并行度, 重试率, SR一次通过率 }
}
```

### 2.3 数据如何驱动优化

**单次执行分析（纵向）：**

```
metrics.md → 发现异常值 → 根因分析 → 定向修复
```

REQ001 的例子：
- "handoff 回报全空" → 发现 SubAgent 不填回报 → 增加三层防御
- "process.log 2 行" → 发现心跳不落盘 → 强制落盘规则
- "21% 超时率" → 发现无超时处理 → 增加超时容忍机制

**多次执行对比（横向）：**

```
metrics[REQ001] vs metrics[REQ002] → 发现趋势 → 结构性优化
```

未来可对比的维度：
- 驳回率是否下降？（质量门禁是否生效）
- 修复循环是否减少？（根因分析是否有效）
- 超时率是否下降？（任务拆分粒度是否合理）
- SR 一次通过率是否稳定？（流程是否成熟）

### 2.4 metrics 的生命周期

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│ 运行时收集   │ ──→ │ 归档时生成    │ ──→ │ 优化时分析    │
│ (.state.md   │     │ (ARC-4 步骤)  │     │ (人工+AI)     │
│  repair_*    │     │ metrics.md    │     │ 对比多份数据  │
│  process.log)│     │               │     │ 定向改进框架  │
└─────────────┘     └──────────────┘     └──────────────┘
```

- **收集阶段**：PM 在运行时自然产生数据（.state.md 的 repair_history、sr_status、task_started_at；process.log 的心跳记录）
- **生成阶段**：ARC-4 步骤中 PM 汇总数据填写 metrics-template.md，保存为 deliverables/{REQ-ID}/metrics.md
- **分析阶段**：人工或 AI 读取 metrics.md，与历史数据对比，发现异常值和趋势，驱动框架改进

### 2.5 设计原则

| 原则 | 说明 |
|------|------|
| 零额外负担 | metrics 数据全部来自运行时已有的状态文件，PM 只需汇总，不需额外收集 |
| 事后生成 | 在 archive 阶段生成，不干扰正常流程执行 |
| 模板驱动 | 使用 metrics-template.md 确保格式一致，便于跨需求对比 |
| 数据>直觉 | 优化决策基于实际数据（"21% 超时率"），而非假设（"可能会超时"） |
| 渐进积累 | 每跑一个需求积累一份数据，样本越多趋势越清晰 |

### 2.6 REQ001 数据总结

| 维度 | 数据 | 结论 |
|------|------|------|
| 端到端成功率 | 1/1 (100%) | 框架可用 |
| SR 一次通过率 | 4/4 (100%) | 决策上下文卡有效 |
| PM 驳回率 | 0% | SubAgent 产出质量达标 |
| 修复循环 | 0 次 | TDD + 质量标准有效 |
| Agent 超时率 | 21% (3/14) | 需要超时容忍机制 |
| Handoff 回报率 | 0% (0/5) | 协议执行严重失败，需三层修复 |
| 日志完整度 | 2 行/预期>10 | 落盘机制缺失 |
| 需求覆盖率 | 93% | 标准需弹性化 |
| 归档质量 | .venv 混入 | 需排除规则 |

**核心发现：框架的"设计层"（角色、流程、门禁）运转良好，但"执行层"（SubAgent 行为、日志落盘、归档细节）存在系统性的"说到没做到"问题。v0.6.0 的优化本质是弥合设计与执行之间的 gap。**
