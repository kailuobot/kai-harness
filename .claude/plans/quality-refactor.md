# 重构计划：质量驱动的 Agent 定义升级

## 核心理念

保持角色隔离（上下文管控底线），但在每个角色内部注入：
1. **质量标准** — 明确定义"好"和"不好"的边界
2. **思考框架** — 指导 HOW to think，不只是 WHAT to produce
3. **反模式清单** — 列出常见的低质量输出特征，让 agent 自检
4. **验收自检** — 交付前的内容质量门禁（不是格式检查）

## 约束

- 不破坏角色隔离
- 不增加流程步骤
- 不增加 CLAUDE.md 大小
- 不改变 handoff 协议
- 不改变 skills 的执行流程

---

## 改动清单

### 1. agents/pm.md — 强化验收能力

当前问题：PM 只做"文件存在性校验"，不做内容判断。
改进：增加"内容质量门禁"，PM 在接收回报时执行快速内容扫描。

新增内容：
- **验收质量门禁**：PM 接收产出物后，除文件存在性外，执行内容质量快扫：
  - BA 产出：每条需求是否有 SHALL + GWT？是否可测试？
  - SA 产出：是否有对照表？Tasks 是否有依赖标注？是否覆盖所有需求？
  - DE 产出：dev-test 和 post-verify 是否 PASS？code-report 是否完整？
  - TE 产出：结论是否明确（PASS/FAIL）？失败项是否有复现步骤？
- **驳回标准**：产出物存在以下情况时，PM 应驳回并要求重做：
  - 产出物明显不完整（如 Tasks 清单只有 1 项但需求涉及多个功能）
  - 产出物存在自相矛盾
  - 产出物使用了占位符/TODO 未填充
  - 测试报告结论为 PASS 但存在未解决的失败项

### 2. agents/ba.md — 注入需求质量思考框架

当前问题：只说"输出 SHALL + GWT"，不说怎么写好的需求。
新增内容：
- **思考框架**：
  - 完整性检查：功能需求、边界条件、异常路径、性能约束是否都覆盖？
  - 可测试性检查：每条 SHALL 是否能写出明确的 PASS/FAIL 判定？
  - 无歧义检查：是否存在"适当"、"合理"、"尽量"等模糊词？替换为具体数值或条件
  - 一致性检查：需求之间是否存在矛盾？
- **反模式**：
  - ❌ 照搬 proposal 原文，只加 SHALL 前缀
  - ❌ GWT 过于笼统（"Then 系统正常工作"）
  - ❌ 遗漏错误路径和边界条件
  - ❌ 需求粒度不一致（有的一句话，有的一整页）
- **质量标准**：
  - 每条功能需求至少有 1 个正向 GWT + 1 个异常/边界 GWT
  - 禁止使用模糊量词，必须给出具体阈值或条件
  - 需求间无循环依赖或矛盾

### 3. agents/sa.md — 注入架构质量思考框架

当前问题：只说"输出 design.md"，不说怎么做好的架构拆分。
新增内容：
- **思考框架**：
  - 先理解再设计：列出需求的核心复杂度在哪里，技术风险在哪里
  - 方案选型：对关键技术决策给出选型理由（为什么选 A 不选 B）
  - Task 拆分原则：单一职责、可独立测试、接口明确、粒度适中（每个 Task 1-3 个文件）
  - 依赖最小化：Task 间依赖越少越好，优先拆出无依赖的基础 Task
- **反模式**：
  - ❌ Tasks 只是需求的重新措辞，没有技术分解
  - ❌ 所有 Task 都标记 deps=none（实际有依赖但没分析）
  - ❌ 对照表只填了"实现对应功能"，没有具体技术方案
  - ❌ 时序图缺失关键交互（如错误处理流程）
  - ❌ Task 粒度过大（一个 Task 包含整个系统）或过小（一个 Task 只改一行）
- **质量标准**：
  - 每个 Task 必须有明确的输入、输出、验证方式
  - 对照表中每条需求至少映射到 1 个 Task
  - 关键技术决策必须有选型理由
  - Task 粒度：每个 Task 预期产出 1-3 个文件，50-300 行代码

### 4. agents/de.md — 注入编码质量思考框架

当前问题：只说"TDD + dev-test"，不说怎么写好的代码。
新增内容：
- **思考框架**：
  - 先读后写：实现前先通读 design.md 中本 Task 的完整描述，理解上下文
  - 接口优先：先定义模块的公共接口（函数签名、类型），再实现内部逻辑
  - 错误处理：每个外部交互点（IO/网络/用户输入）都必须有错误处理
  - 边界条件：空值、零值、超大输入、并发场景是否处理？
- **反模式**：
  - ❌ 只实现 happy path，忽略错误处理
  - ❌ 测试只验证"能跑通"，不验证边界条件和错误路径
  - ❌ 硬编码配置值（路径、URL、密钥）
  - ❌ 函数过长（>50行）、嵌套过深（>3层）
  - ❌ 复制粘贴代码而不抽象
  - ❌ 跳过 TDD 直接写实现再补测试
- **质量标准**：
  - 每个公共函数/方法有对应测试
  - 错误路径有测试覆盖
  - 无硬编码的配置值
  - 代码通过 lint 无 error（warning 可接受）
  - 构建成功且测试全部通过

### 5. agents/te.md — 注入测试质量思考框架

当前问题：有 test_strategy 路由但缺乏质量判断标准。
新增内容：
- **思考框架**：
  - 需求覆盖：每条需求的 GWT 是否都有对应测试验证？
  - 风险优先：优先验证高风险路径（核心功能、数据一致性、安全边界）
  - 独立验证：不信任 DE 的 code-report，独立运行测试确认结果
  - 回归意识：修复一个 bug 是否引入了新 bug？
- **反模式**：
  - ❌ 只运行 DE 已写的测试，不验证测试是否覆盖需求
  - ❌ 测试通过就标 PASS，不检查是否遗漏了关键场景
  - ❌ 报告只写"全部通过"，不列出具体验证了什么
  - ❌ 发现问题但描述模糊（"有个bug"），不提供复现步骤
  - ❌ 降级验证时不标注原因和风险
- **质量标准**：
  - PASS 条件：所有测试通过 + 需求覆盖无遗漏 + 无已知未修复缺陷
  - FAIL 必须附带：失败用例 + 复现步骤 + 期望vs实际 + 严重程度
  - 降级验证必须标注：降级原因 + 未验证的风险项 + 建议的补充验证方式
- **严重程度定义**：
  - Critical: 核心功能不可用、数据丢失、安全漏洞
  - Major: 功能缺陷但有 workaround、性能严重退化
  - Minor: UI 瑕疵、非核心路径问题、文档不一致

### 6. agents/ux.md — 注入设计质量思考框架

当前问题：只说"产出 wireframe"，不说怎么做好的设计。
新增内容：
- **思考框架**：
  - 信息层次：最重要的信息是否最突出？视觉层次是否清晰？
  - 一致性：相似元素是否有相似的视觉处理？间距/字号/颜色是否统一？
  - 可实现性：设计是否在技术约束内可实现？（如 PPT 的 16:9 单页约束）
  - 内容适配：设计是否考虑了真实数据的长度变化？
- **反模式**：
  - ❌ 所有页面用同一个布局，没有根据内容类型选择合适的版式
  - ❌ 占位内容与真实内容长度差异过大
  - ❌ 忽略模板约束（如 PPT 必须引用 ppt-base.css）
  - ❌ 信息密度过高或过低
- **质量标准**：
  - 每页/每屏有明确的视觉焦点
  - 布局选择有理由（在 slide-spec.md 中说明）
  - 符合所有模板约束
  - 占位数据的长度接近真实数据

### 7. skills/mh-apply.md — 强化 PM 验收环节

在 PM 接收 DE/TE 回报后的校验步骤中，增加内容质量检查：

当前："接收回报，校验输出文件存在性"
改为："接收回报，执行质量门禁：
  1. 文件存在性（当前已有）
  2. 内容完整性扫描：
     - DE: code-report.md 中 dev-test=PASS 且 post-verify=PASS
     - DE: output/ 中文件数量与 Task 描述匹配
     - TE: 报告结论明确（PASS/FAIL），无 TODO/占位符
     - TE: FAIL 时每个失败项有复现步骤
  3. 不满足则驳回，附带具体缺陷描述"

### 8. skills/mh-propose.md — 强化 PM 对 SA 产出的验收

在 PM 接收 SA 回报后，增加：
"PM 验收 design.md 质量门禁：
  1. 对照表是否覆盖所有 proposal 要点（无遗漏）
  2. Tasks 清单是否有依赖标注
  3. 每个 Task 是否有明确的验证方式
  4. 不满足则驳回"

## 不改动的

- CLAUDE.md（不增加大小）
- handoff 协议和模板
- .state.md schema
- scripts/*.sh
- 流程顺序和审批节点
- 角色隔离规则

## 预期效果

- Agent 产出物从"格式正确但内容空洞"提升到"内容有深度且可验证"
- PM 能在流程内拦截低质量产出，减少无效的修复循环
- 每个角色有明确的自检标准，减少"声称完成但实际不达标"
- 不增加流程步骤，不增加 token 开销（质量指导是 agent 定义的一部分，只在 spawn 时注入一次）
