# v0.6.1 上下文效率优化计划

基于架构审视，本轮聚焦"减少 PM 运行时噪音"和"修复文档不一致"。

---

## 改动清单

### 🔴 P0-1: mh-apply.md 拆分

**当前**: 328 行单文件，PM 每次加载全部 3 种模式 + 修复循环。
**目标**: PM 只加载主文件 + 当前模式子文件，修复循环按需加载。

拆分方案：
```
skills/mh-apply.md              → 主文件（前置检查+断点续作+模式路由+异常处理），~80 行
skills/mh-apply-fast.md         → fast 模式流程，~55 行
skills/mh-apply-standard.md     → standard/full 模式流程（含 SR2/SR3），~120 行
skills/mh-apply-repair.md       → 修复循环（根因分析+收敛追踪+派发），~75 行
```

主文件中的模式路由：
```markdown
## 模式路由

- fast 模式: 读取 `skills/mh-apply-fast.md` 执行
- standard/full 模式: 读取 `skills/mh-apply-standard.md` 执行
- 修复循环（任何模式 FAIL 时）: 读取 `skills/mh-apply-repair.md` 执行
```

**PM 运行时负载变化**:
- 之前: pm.md(159) + mh-apply.md(328) = 487 行固定
- 之后: pm.md(159) + mh-apply.md(80) + mh-apply-standard.md(120) = 359 行（standard/full）
- 之后: pm.md(159) + mh-apply.md(80) + mh-apply-fast.md(55) = 294 行（fast）
- 修复循环按需加载: +75 行（仅 FAIL 时）

**注意**: full 模式与 standard 模式的 apply 阶段完全一致（区别仅在 propose 阶段），合并为一个文件。

### 🔴 P0-2: mh-clarify.md 环境预检压缩

**当前**: 环境预检占 ~75 行（第 22-74 行），逐语言枚举检测规则。
**目标**: 压缩为原则性指引 ~20 行。AI Agent 有能力自己推断"看到 Cargo.toml 就是 Rust"。

压缩后：
```markdown
## 环境预检

1. 扫描项目根目录，检测技术栈：
   - 语言: 通过配置文件推断（pyproject.toml→Python, package.json→Node.js, go.mod→Go, Cargo.toml→Rust, pom.xml/build.gradle→Java）
   - 包管理器: 通过 lock 文件推断
   - 测试框架: 通过配置文件中的 test 相关配置推断
   - 构建工具: 通过 build 相关配置推断
   - Lint 工具: 通过 lint 配置文件推断

2. 浏览器可用性检测（仅 output_type 涉及 UI 时）：检测 Playwright/Selenium/Cypress

3. 将检测结果写入 `deliverables/{REQ-ID}/.state.md` 的 tech_stack 和 env 字段

4. 如检测结果不完整或 language=unknown，向用户展示检测结果并请求补充
```

**行数变化**: mh-clarify.md 从 256 行降到 ~200 行（-56 行）。

# 增加 output_files 非空检查
if grep -q 'output_files: \[\]' "$handoff" 2>/dev/null || grep -q '^output_files: $' "$handoff" 2>/dev/null; then
    echo "WARN: $(basename "$handoff") output_files 为空"
    empty_report_count=$((empty_report_count + 1))
fi
